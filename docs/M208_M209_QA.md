## M209 — Cross-device convergence hardening

The VK Storage adapter already uses versioned chunks, a checksum, an epoch and a pointer published last. VK Bridge, however, does not provide an atomic compare-and-swap on that pointer.

Changes:
- On clean `sync()` calls (already invoked on focus and on the existing 25-second heartbeat), compare the remote epoch and small manifest pointer; **download full save chunks only if the generation changed**.
- When a different generation is found, perform a same-account merge against the previous cloud baseline; upload if local state contains information not present remotely.
- After publishing new chunks and index, verify the current epoch and pointer. If another writer replaced it before acknowledgment, merge and retry rather than falsely reporting "saved".
- Repeated `sync()` calls during a running upload coalesce without spuriously marking progress dirty; actual progress updates continue to mark dirty in `changed()`.
- Bump VK adapter cache key in `index.html` for release.

New regression scenarios:
1. A clean second device discovers another device's save.
2. Unchanged pointer incurs only one small storage read, no chunk download.
3. Pointer replaced before first device's acknowledgment is detected and reconciled.
4. Clean check still rejects an account reset/changed epoch.
5. Two devices **both finish and acknowledge stale independent writes**, so the remote pointer temporarily omits one device's stars; the surviving device's subsequent heartbeat merges and republishes both sets. This test explicitly demonstrates the **non-atomic gap**.

### Limitations — do not overclaim

The adapter now offers **best-effort eventual convergence if at least one device retains its local save and later synchronizes**. It does **not guarantee transactionally consistent or serializable writes**. If multiple devices overwrite each other and all are uninstalled/reset before reconciling, information may be lost. A strict guarantee requires a transaction-capable backend or API-supported CAS/version conditions. Coins and spending require separate conflict policies, not a naïve `max(balance)` merge.
